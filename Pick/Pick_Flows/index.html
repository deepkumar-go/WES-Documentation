How flows are determined
Flow Selection

Pick flows are determined by PPS station configuration (post_pick_agent), not by order type. Each flow encodes its own bin allocation strategy, rack gating logic, and post-pick destination routing. The same order can run through different flows depending on which station picks it.

The Six Flows
①
Standard GTP — Vanilla Bin
pick_front_hsm · pick_front_fsm
post_pick_agent: bin

The most common flow. Autonomous bots transport racks to a PPS station. An operator scans slots, picks items into pre-allocated bins, and signals completion via PPTL. Bins exit on a consolidation belt for downstream dispatch.

Bot transports rack→ Rack arrives at PPS→ Operator picks items→ PPTL bin full→ Bin → consolidation belt
AspectDetail
Bin allocationPre-allocated by bin_planner; multiple orders can share one bin
Rack gatingRack release blocked until bin destination is available (is_pick_possible/2)
Throughput modelHigh-velocity short picks; UPH maximised via rack tier selection (A→A'→B→C→Stored)
DestinationConsolidation belt → ship lane
Bin signalOperator presses PPTL (Pick-to-Tote Light) when bin is full
Optional featuresTwo-stage bin, case-level picking, partial pick, packing box, MSIO
Use caseStandard e-commerce fulfilment — high SKU variety, low qty per SKU
②
EasyLoop — Single PPS Carousel
pick_front_single_pps_hsm
post_pick_agent: easyloop_bin

A carousel model where a single PPS station cycles racks continuously. The system (HTM) owns destination allocation rather than the operator. Designed for very high-velocity environments where manual bin assignment would become a bottleneck.

HTM assigns destination→ Rack loops to single PPS→ Operator picks (one slot)→ Rack loops back→ Fixed relay lane exit
AspectDetail
Bin allocationSystem-managed (HTM-orchestrated); one order per slot
Station topologySingle PPS — racks cycle in a closed loop back to the same station
Throughput modelSustained high UPH; no pause between rack arrivals
DestinationFixed relay lane managed by HTM
Rack gatingNo gate — system allocates continuously; easyloop_bin node handles destination
Optional featuresPick-and-pass (pass order to next station in the loop)
Use caseHigh-volume retail or grocery fulfilment (e.g. Walmart-style deployments)
③
Shuttle / Looped Relay
pick_front_hsm (looped variant) · shuttle_carrier_exception_node
post_pick_agent: shuttle

Items are picked onto shuttle trays that move via conveyor to consolidation points. A single shuttle carrier can hold multiple orders. The flow includes shuttle-specific carrier validation, pre-drop level checks, and belt exception handling.

Bot transports rack→ Operator picks → tray→ Shuttle carrier validation→ Tray on conveyor→ Consolidation point
AspectDetail
Bin allocationTray managed by shuttle system; system-allocated destinations
Station topologyMultiple PPS stations share a looped shuttle conveyor
Throughput modelSpeed-optimised; conveyor removes human wait time between picks
DestinationShuttle consolidation point → dispatch
Exception handlingDedicated shuttle_carrier_exception_node (belt faults, level-order mapping)
Relay thresholdControlled by va_relay_threshold — switches between relay and direct routing
Use caseApparel, footwear — tray-based high-speed systems
④
Zerowalk / TSORT — Sortation-Driven
pick_front_hsm · wait_for_entity_pre_drop_node · post_scan_node
post_pick_agent: tsort / rms

Items are picked directly into sortation chutes or trays without a relay mechanic. The "pre-drop" model means the operator signals placement on the rack slot itself (zerowalk) or into a sort chute (TSORT). Post-pick destination routes straight to a sortation system.

Bot transports rack→ Operator pre-drops item→ Post-scan confirm→ Sort chute→ Sortation lanes → packing
AspectDetail
Bin allocationSort chute or pre-drop slot; no traditional bin
Station topologyBots bring racks; items placed directly into sort infrastructure
Throughput modelSortation-enabled; downstream sorter handles order consolidation
DestinationSortation lanes → packing
Zerowalk variantOperator signals pre-drop complete; optionally gated by enable_bin_full_in_zerowalk
Optional featuresBarcode validation bypass (zw_skip_barcodes_validation), MRU/MTU flow variants
Use caseSort-to-tote fulfilment; facilities with sorter infrastructure
⑤
RMS — Reserve Management System
pick_front_hsm · wait_for_rms_dest_node · rms_picklist_filter_node
post_pick_agent: rms

Orders pull inventory from deep-storage or reserve racks into the forward picking area. Primarily used for stock rotation and replenishing forward-area slots when they run low. Has its own destination node and picklist filter.

Reserve rack identified→ Bot transports to PPS→ Operator picks to reserve bin→ Forward area induction→ Slot replenishment
AspectDetail
Bin allocationReserve bin; allocated for inbound replenishment
Station topologyDeep storage rack → PPS → forward-area induction queue
Throughput modelReplenishment-focused; not optimised for unit throughput
DestinationForward-area induction → slot replenishment
Belt configPhysical belt dimensions set via rms_belt_dimension
Use caseDOH management; preventing stockouts in forward picking area
⑥
RPick — Retail / Reserve Pick
rpick_hsm · rpick_analytics_manager · rpick_aisle_functions
Separate HSM

A completely separate HSM (rpick_hsm) for reserve-area picking where rangers physically walk aisles rather than bots bringing racks. Rollcage-based, with item/container scanning, transfer request handling, and dedicated analytics tracking.

Transfer requests checked→ Ranger docks rollcage→ Walks aisle, scans items→ Clean scan confirm→ Print confirm → transfer
AspectDetail
Bin allocationRollcage bins; ranger fills as they walk the aisle
Station topologyNo bots — ranger navigates reserve aisles autonomously
Throughput modelVerification-focused; accuracy over speed
DestinationRollcage → transfer to forward area or audit queue
ScanningItem barcode scan + container barcode scan + post-pick clean scan
Transfer requestsChecks pending inter-aisle transfer requests before each pick cycle
AnalyticsDedicated rpick_analytics_manager tracks ranger UPH and pick variance
Aisle managementOvercrowding penalty + same-aisle reward to balance ranger distribution
Use caseStock rotation, variance reconciliation, reserve area replenishment
Architecture
FSM vs HSM — Coexistence

Both coexist — it is not a full migration. FSMs remain active for PPS configurations that have not moved to the HSM path. The toggle is per-station via use_hsm_for_pick_front.

FSM (Legacy)HSM (Current)
Modulespick_front_fsm, pick_back_fsm, rc_pick_back_fsmpick_front_hsm, pick_front_single_pps_hsm, rpick_hsm
StructureFlat — all ~30 states in one moduleHierarchical — each state is its own node module
Transitionsgen_statem callbacks with explicit state functionsNode graph via {subproc, NextNode, …}
Exception handlingInline in state functionsDedicated exception node subtrees per flow type
Flows supportedBasic pick workflows; limited to flat state modelAll 6 flows including EasyLoop, Shuttle, RPick
StatusActive for legacy PPS configsPreferred for all new flows and station types
TogglePer-PPS via use_hsm_for_pick_front (PPS-level config)
