Pick — Order Fulfillment Engine

Orchestrates the complete lifecycle of warehouse order fulfillment: from order receipt through scheduling, physical picking at robotic stations (PPS), bin planning, volumetric fitting, tote packing, and WMS export. Supports 10+ station hardware variants via interchangeable FSM/HSM implementations.

Order Received
An order arrives via the Kafka topic pick_request.events (event: order_allocated) and is picked up by pick_request_event_handler. The handler validates the payload, writes an incoming_order record to Mnesia, and notifies order_manager that a new order is available for processing. At this point the order is in pending status and sits in the scheduler's input queue, waiting for the next scheduling cycle.
order_manager — Pending Queue

order_manager (429 KB) is the central coordinator for all active orders. It also handles order modifications (cancellations, quantity changes, additions) mid-flight. Orders move from pending → in_process once selected.

Scheduling cycle — when does it trigger?

The cycle is event-driven and per-PPS — not time-based or batch-sized. process_orders() is called from ~20 different places whenever something changes that could free up capacity: an order arriving, a bin being released, a carrier completing a pick, or an order modification finishing. A fallback periodic timer (auto_order_processing_interval, default 30 ms) fires if no event has triggered a cycle — this is a safety net, not the primary driver.

Within a cycle, process_orders_internal runs in a spawned process (keeping the gen_server responsive). It selects one PPS per cycle using round-robin across stations that have free bins. A calculation_status = true guard prevents two cycles overlapping — so at any moment there is at most one in-flight calculation process per order_manager.

Inventory availability — what is checked?

get_item_counts_going_to_pps_v2 builds an ItemDict — 8 dictionaries (one per rack tier) each mapping tpid → available quantity visible from the selected PPS at the moment of the cycle. For each pending order the scheduler asks: does the ItemDict contain enough quantity across these tiers to fulfil every line item?

Tier What it represents
A+Rack at the PPS port, IDC distance cost below threshold — effectively already there
ARack tasked to this PPS, en-route or at port
A1Other faces of the same Tier A rack
BRack tasked to a hopping (neighbouring) PPS
CRacks available in aisle / storing state
DPenalised racks (deprioritised but still eligible)
EEntities derived from existing tier racks
FRemaining published entities not in any other tier

The check is tier-aware — orders whose items sit in Tier A get a higher scheduling score than those requiring Tier C racks, because transport cost is lower. The ItemDict is cached in items_to_pps_cache (configurable TTL, default 0 = rebuilt each cycle) to avoid redundant Mnesia reads across all orders in the same cycle.

pick_scheduler — Strategy Selection
pick_scheduler selects one scheduling strategy per cycle from: ppf (picks-per-formation, weight 10), pbt (pick-by-time, weight 4), pbt_breached / pbt_rob (SLA breach / at-risk, weight 3 each), plus piggyback, grouped, and critical. The strategy determines which orders are eligible and how they are ranked. Capacity ETS caches (system_pick_capacity_ets, tasked_picks_per_flow_ets) gate whether new work can be issued to a PPS at all.
rack_selector — Tiered Rack Selection
rack_selector (66 KB) picks the best source rack for a given order using a four-tier cost model: Tier A (rack already at the PPS port), A' (en-route to PPS), B (available in aisle), C (requires robot dispatch), and Stored (deep storage). The selector also considers inventory split across slots, carrier weight limits, and whether a rack is already reserved by another order to avoid contention. The result is a ranked rack list attached to the order_node.
bin_planner — Bin Allocation
bin_planner (42 KB) assigns a physical PPS bin to the order before the carrier arrives. It checks available bins via ppsbin records (status: idle), applies volumetric fitting from the cubing/ subsystem to verify the order's items will physically fit, and reserves the bin by transitioning it to in_use. For multi-picklist flows, multiple bins may be reserved in a single planning pass. If no bin is free, the order waits in waiting_for_free_bin state.
PPS Station — FSM / HSM Active
Once a bin is reserved and the carrier is en-route, the station's FSM or HSM takes over. Plan transport nodes (wait_for_source_arrival_node, picklist_processing_*_node) gate entry until the carrier physically arrives and is validated. The operator then works through entity transport nodes — scanning the carrier, confirming picks item-by-item, and handling exceptions. The exact node graph depends on station type: legacy pick_front_fsm for dockable/rtp, pick_front_hsm for shuttle/zerowalk, or pick_front_single_pps_hsm for easyloop.
Pick Confirm — item_picked Event
When the operator confirms a pick (or autopick confirms it automatically), a item_picked event is published to order-pick-updates.events. pick_kafka_handler consumes this, updates the pick_instruction status to completed, decrements the in-flight inventory count, and advances the order_node. When all instructions for an order are complete the node transitions to picked. The back FSM (if present) then handles bin sealing, tote release, and publishes bin_complete.events.
WMS Export — Order Complete
Completed orders are exported to the Warehouse Management System via order_export_server and pick_order_export_http_controller. A Kafka event is published to wms.pick.orders.export.v1 carrying the final order line details, quantities, and bin/tote associations. The order_node status advances to consolidated → shipped as downstream systems acknowledge receipt. order_information.events is also published to notify other internal consumers of the final state.

Classic vs Streaming

Classic: Each order processed end-to-end before the next begins. Compatible with all PPS types.

Streaming (app flag streaming_orders): Pipeline processing — orders flow through stages concurrently. Uses order_streaming_manager + streaming_order_inventory tables. Two sub-implementations: v0 (117 KB) and v1 (176 KB).

Autopick

Automated pick confirmation without operator intervention. Managed by auto_pick_front_server and autopick_event_handler.

Transactions tracked in the autopick_transaction table: created → processed → confirmed

Enabled per-PPS; autopick event handler drives confirmation when operator scan is bypassed.

Multi-Picklist Orchestration

When multiple picklists are simultaneously active for a PPS, multi_picklist_orchestrator (29 KB) coordinates them — enabling one station to process batched orders across multiple racks in parallel. Bin planning is handled cooperatively with the picklist_processing_*_node variants.

Type Conventions

Per CLAUDE.md rule #3 — -opaque for Mnesia records; -type for non-DB records.

%% Mnesia → -opaque (hides internal structure)
-opaque order_node() :: #order_node{}.
-opaque ppsbin()     :: #ppsbin{}.
-opaque inventory()  :: #inventory{}.

%% Non-DB → -type
-type pick_config() :: #pick_config{}.
-type scheduler_weights() :: #{
    ppf  := integer(),
    pbt  := integer(),
    ...
}.

Callers use typed accessor functions only — e.g. ppsbin:get_status/1, never raw record pattern-matching on Mnesia tables.

Integration Pattern — Saga-Wrapped Kafka

All Kafka publishing must be wrapped in gen_saga:promise inside a ?MNESIA_TRANSACTION. This guarantees events fire only on successful commit (CLAUDE.md rule #7).

%% CORRECT — event fires only if transaction commits
?MNESIA_TRANSACTION(fun() ->
    mnesia:write(UpdatedRecord),
    gen_saga:promise(pick_kafka_publisher, publish_order_update,
                     [OrderId, Status])
end)

%% Publisher module:
%% apps/pick/src/interfaces/out/pick_kafka_publisher.erl

Direct calls to kafka_produce_sync_promise from business logic are prohibited — all publishing routes through the app-specific publisher module.

Conventions

No EUnit — all tests including unit-level must be written in Common Test.

Async events: Use butler_ct_utils:loop_test_events/3 instead of timer:sleep to avoid flaky tests.

Mocking: meck in tests only; always meck:unload/1 in cleanup. Never in production code.

Mnesia setup: Each CT suite must use pick_ct_setup to initialise required tables before test cases run.
